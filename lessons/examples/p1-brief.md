# 示范：P1 的 brief

下面这份 brief 可以原样发给 Haiku 子 agent。每一段后面的 › 注释说明这一段为什么要写，**发给子 agent 时要删掉这些注释**。

---

## 1. 目标

实现 `hw1/cs329z_hw1/adapters.py` 里的 `run_priority(email, lm)`：用一次模型调用，判断一封邮件对收件人来说是 `urgent`、`normal` 还是 `ignore`，并给出一句理由。完成后，`uv run pytest tests/test_priority.py` 的确定性测试全部通过。

› 一句话说清"做完后什么变了"，再加上可以检查的终点。

## 2. 真相来源（按这个优先级）

1. `hw1/cs329z_hw1/adapters.py` 里 `run_priority` 的 docstring，这是规格。
2. `hw1/tests/test_priority.py`，测试实际检查什么。尤其要看 `REPLIES` 和 `NO_LABEL`：测试会塞给你 12 种乱七八糟的模型回复。
3. `hw1/data/priority_rubric.md`，标签的判断标准。prompt 要基于它来写。
4. `hw1/cs329z_hw1/llm.py`，看 `LM` 和 `ScriptedLM` 的接口，以及 `OutputTruncated` 和 `BudgetExceeded` 两个异常。
5. `hw1/cs329z_hw1/types.py`，看 `Email` 的字段。

如果这些文件和本 brief 冲突，以文件为准，并在汇报里指出冲突在哪里。

› 子 agent 看不到我们的对话，所以要告诉它去读什么、谁说了算。"冲突时以文件为准"能防止它照着我写错的地方去做。

## 3. 约束和非目标

- 只能改 `hw1/cs329z_hw1/adapters.py`，或者在 `hw1/cs329z_hw1/pipelines/` 下新建文件。
- 不许改 `tests/`、`data/`、`llm.py`、`types.py` 等任何 provided 文件。
- 不许修改 `pyproject.toml`，不许加依赖，不许用任何 LLM 或 agent 框架。
- 所有模型调用都只能走传进来的 `lm` 参数。不许自己创建 `LM()`，不许访问网络。
- 不许修改传进来的 `email` 字典。
- 不许跑实时测试（`-m live`）。
- 不许为了通过测试而针对测试里的固定字符串写特判。
- 不做 P2 及以后的任何题。

› 这一段防的是 AI 最常见的三种越界：改测试、加依赖、顺手多做。"不许针对测试字符串写特判"防的是作弊，就是 L11 讲的奖励作弊在编码里的样子。

## 4. 设计决定

**我已经定了：**

- prompt 要求模型先写一句理由，最后一行严格按 `LABEL: <urgent|normal|ignore>` 的格式输出。
- 解析器从回复里找这个格式。找不到合法标签时，返回 `unknown`，同时给一个非空的默认理由。

**留给你定（每一项都要在汇报里写出你的选择和理由）：**

- a) 回复没有按格式写、但正文里**恰好只出现一个**标签词时（比如 `"I would say this one is Normal."`），要不要接受？注意：`NO_LABEL` 里的回复必须得到 `unknown`；出现两个以上标签词时不许猜。
- b) rubric 放多少进 prompt：全文、摘要，还是摘要加例子？要考虑到实时测试用的是另外 60 封邮件。
- c) 邮件的哪些字段放进 prompt（`from`、`to`、`date`、`subject`、`body`），超长的 body 要不要截断、截到多长。
- d) 模型调用抛出 `OutputTruncated` 时怎么办（docstring 要求函数不能抛异常）。抛出 `BudgetExceeded` 时要不要也接住？接住的话，预算上限就失效了。

› 一共四个决定。我先定了"格式"，因为它决定了解析器怎么写，属于架构；把"宽松解析、rubric 放多少、哪些字段、异常怎么处理"交出去，并要求它说出理由。最后一项 d 是故意埋的坑：两个要求互相拉扯，想看它会不会注意到。

## 5. 验收

在 `hw1/` 目录下运行：

```bash
uv run pytest tests/test_priority.py -q
```

要求所有非 live 测试都通过，也就是 24 个参数化用例加 `test_email_is_not_modified`。

没通过时，最多自己修 3 轮。还过不了就停下，原样汇报失败的测试名和报错信息。不许改测试来让它通过。

› 验收是一条命令加一个数字。"最多 3 轮，然后停"是 HW1 P7 里 malformed 计数的同一个思路，用在子 agent 身上。

## 6. 汇报格式

1. 改了或新建了哪些文件，每个文件一句话说明。
2. 设计决定 a–d：你的选择，每项一到两句理由。
3. 最终 pytest 的输出，原样贴最后 3 行。
4. 你注意到、但没有处理的问题。
5. 你不确定的地方。

› 要求原样贴测试输出，是为了防止它"口头宣布成功"。"注意到但没处理的问题"给它一个出口，让它不必为了显得完成而把问题藏起来。

## 对照：一份坏的 brief

> 帮我实现 run_priority，让 tests/test_priority.py 通过，用一个好的 prompt。

| 缺了什么 | 后果 |
|---|---|
| 没有真相来源 | 它可能不读 rubric，prompt 凭常识写，实时测试过不了 85% |
| 没有约束 | 它可能改测试、自己 `LM()`，或者顺手写 P2 |
| 没有设计决定 | 宽松解析、异常处理这些都被它默默定了，你不知道，也没法验收 |
| "好的 prompt"不可检验 | 你和它对"好"的理解不一样 |
| 没有汇报格式 | 它说"完成了"，你只能信或者不信 |

## 我的事前预测（示范：每份 brief 你都要写一段）

1. 最可能出错的是**宽松解析**：Haiku 可能写一个"找到任何标签词就用"的解析器，结果把 `"urgent? normal? ignore?"` 判成 urgent。测试不会因此失败，但违反了"不许猜"的精神。
2. 它很可能没注意到 d 里的矛盾：要么把所有异常都吞掉，包括 `BudgetExceeded`；要么一个都不接。
3. 它可能根本不提 rubric 放了多少，那就说明它没认真读第 4 段。
